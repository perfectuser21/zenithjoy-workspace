# 小改动 PrepPRD：私信触达日发送上限阶梯测试 + 自动熔断安全网

## 改什么

**范围：金诺租户两个触达小号（`langzi63485`=jinoshengyuan-work, `44997267357`=legacy），`services/phone-adb-controller/outreach-tick.sh` + 新增配置/纯函数库。**

### 背景
用户拍板：现有19条/天（8-21点，两号轮流）是主理人自己压低的保守值，从未做过真实平台限流/封号阈值测试。现在要用两个号分别测两种升量方式，找出真实上限，同时把发送节奏做得更不机械。用户明确知情且接受"拿真账号测边界"的风险。

### 1. 时间窗口
- 两个号的 crontab tick 窗口从 `*/30 8-21` 改为 `*/30 0-23`（全天24小时，不再局限工作时间）。

### 2. 两种升量方式（用户拍板：一号一种）
- **jinoshengyuan-work（逐日阶梯）**：以 2026-09-20 为起点，每日目标发送量比前一天 +5，从当前 ~10/天起步，直到触顶或触发熔断。
- **legacy（单日内快速阶梯）**：每天内每 3 小时目标发送量 +5，从当前 ~10/天起步的档位开始，一天内多次升档，更快摸到阈值。
- 两条曲线都设一个理智天花板（60/天），到顶后不再升，防止无限期加压。

### 3. 每日发送上限执行机制
- 新增纯函数库 `services/phone-adb-controller/dm-rate-ramp-lib.js`：`computeDailyCap(config, profileKey, now)` 按 profile 的升量模式算出"今天/此刻允许发到多少条"。
- `outreach-tick.sh` 每次 tick 先读本机计数文件 `~/bin-harvest/state/dm-count-<profile>-<date>.txt`（今日已发数），超过当日上限就直接跳过（视为"今日已到量"，不算受阻，不占用受阻队列）。
- 每次真实 send_status=sent 或 restricted（消耗了一次真实发送尝试，仍要计入）后，计数文件 +1。

### 4. 自动熔断（安全网，防止真的把号弄坏）
- 扩展 `outreach-tick.sh` 的 `classify_failure`：当归因为 `other`（未识别的新失败模式，历史失败分类里都没见过的）时，把完整原始设备输出追加写入 `~/anomaly-<profile>.log`，并让该次失败计入"异常计数"。
- 同一 profile 连续出现 **2 次** `other` 类异常（不含已知的 transient/terminal 分类），立即写一个熔断标记文件 `~/bin-harvest/state/dm-paused-<profile>.flag`；tick 开头先检查这个文件，存在就整个跳过本次 tick（不发送、不升档），直到人工确认清除。
- 这就是"测出真实上限"的判定依据：熔断触发的那一刻的当日发送量，就是本次测试拿到的真实阈值证据。

### 5. 去机械感（用户要求，本轮一并做）
- 发送前停顿从固定"3-8秒"改成更宽的"5-25秒"随机区间。
- tick 内延迟从"0-8分钟"改成"0-20分钟"随机区间，弱化"整点/半点必发"的规律感。
- 30%跳过概率不变（已经是原有拟人纪律）。

## 为什么改
员工反映人工触达28次后账号被限；系统当前19条/天是刻意压低值，从未验证真实上限；用户要求在24小时运营假设下用两种升量方式实测，同时降低发送节奏的机械感。

## 影响范围
