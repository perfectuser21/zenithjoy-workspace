# Bug PrepPRD：评论意向分档判定真机验证时发现，2/3 视频的 Gemini 判定结果完全解析失败

## 症状

PR #1412（评论意向分档判定）合并部署后，真机重跑一次采集任务验证：3 个视频、13 条评论区留言，只有 1 个视频的 4 条留言里的 3 条被真实打上"感兴趣"档位，其余 2 个视频的全部留言（含明显高意向的"预算10万求推荐""预算20w内能不能包入住？能不能给我做一下预算？"）grade 全部是 null。服务端日志里没有任何 `[comment-grading]` 报错——说明 Gemini 调用本身成功了，是解析阶段丢的数据。

## 根因假设

`apps/api/src/services/comment-grading.ts` 的 `parseGrades()` 用正则 `/^\s*(\d+)\.\s*(高意向|精准|感兴趣|其他)/` 匹配 Gemini 回复的每一行，只认半角句号 `.` 作为序号分隔符。Gemini 用中文 prompt 回复时经常会用全角标点（`。`/`、`）而不是半角句号，这条正则匹配不上，导致该行被跳过、对应位置留 null。

真机证据支持这个假设：3 个视频里恰好 1 个"整批解析成功"、2 个"整批解析失败"——如果是随机的评论质量问题，不会呈现"按视频批次二值化"的模式；如果是格式问题（Gemini 这次回复整体用了全角标点），一整批全部匹配失败正是预期表现。同一批次内还有1条（"我在内黄有套房，不知道怎么装修"）单独失败，与"该行格式跟其余几行不完全一致"的假设吻合（Gemini 单条输出不稳定，偶尔单行也会用不同标点）。

代码审查阶段（PR #1412 Task 3 review）已经把这个列为 Minor 风险提前预警过，真机验证证实它是真实、高频发生的问题（3 批里 2 批全军覆没），不是理论边界情况。

## 修法

1. `parseGrades()` 的正则放宽序号分隔符，同时接受半角句号 `.`、全角句号 `。`、顿号 `、`：
   ```ts
   const lineRe = /^\s*(\d+)[.。、]\s*(高意向|精准|感兴趣|其他)/;
   ```
2. 新增诊断日志：解析后如果命中数少于 comments.length（部分或全部解析失败），打印一条 `console.warn` 带上原始响应文本（截断到合理长度），下次再发生这类问题不需要再上真机翻数据库猜，日志直接能看到 Gemini 原始回复长什么样。

## Regression Test 计划

`comment-grading.test.ts` 新增用例，覆盖真机实测复现的具体场景：
- Gemini 响应整体使用全角句号（`1。高意向\n2。精准`）→ 断言全部正确解析（当前实现会全部返回 null，这条测试在修复前必现 FAIL）
- Gemini 响应混用全角/半角（`1. 高意向\n2、精准\n3。感兴趣`）→ 断言全部正确解析
- 部分行解析失败时，`console.warn` 被调用且带上原始文本片段

## proven-to-fire 守卫

Regression test 本身即逻辑接缝守卫：commit-1 阶段用真机复现的确切格式（全角句号）写 failing test，实测会 FAIL（当前正则命中不了），commit-2 后转绿。这是真实真机数据驱动的测试，不是凭空构造的边界 case。
