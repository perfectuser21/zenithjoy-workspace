# 路②「协同笔记/文档」Golden Path 定义 v1（三镜头 GAN 收敛版，呈主理人拍板）

**一句话**：〔员工要写一篇文档（会议纪要/SOP/方案/项目 wiki），当前散在飞书文档/Notion/本地〕→〔在 Staff Hub 里建文档、写富文本、组织成文档树、多人协作**不静默覆盖**、按组织权限管得住、AI 一等公民能读能写回且受同一权限约束不投毒、与经验打通，数据按组织隔离、可导出拿走、删错可恢复〕

**line 定位**：line11 员工知识中枢 = 员工的 Notion（知识+**文档**+数据三合一）。路①经验（已合并 PR#1670）/路②文档（本定义）/路③database（已合并四刀）共此一线。journey=da60cb26，主理人拍板决策 ab866172（多组织三层权限/SSOT=Cecelia 账本团队库只读投影/AI 横切接自有 LLM）。

**客户/付钱人**：多组织员工团队的主理人——替代飞书文档/Notion 文档订阅；感知者=写文档、协作、查文档的一线员工与 agent。

## 主理人拍板（2026-08-22，本 v1 基础上定案，进 capability-controller 深化）
- **Q1 协作模型：实时版 CRDT（多人光标，像腾讯文档）** —— 一步到位实时协同，**不是**乐观锁 thin。⚠️ 这是重决策、工程量大：实时同步引擎是**净新增**（路③无乐观锁/version 列可复用），controller 提案须如实评估规模 + CRDT 库选型（Yjs/Automerge 对比推荐）+ 实时 WS 通道方案。S2 承诺随之升级为「真·多人同时编辑、字符级合并、多人光标」，本文 S2 的乐观锁 thin 表述作废，以 CRDT 为准。
- **Q2/Q4 导入：首刀不含导入**，新文档从零写（Notion/飞书批量导入留后续）。
- **Q2 检索**：显式标记「可被 AI 检索」才进检索域（非全部文档进）——采纳推荐默认。
- **Q3 三层中间层**：显式指定成员集合，不建部门表——采纳推荐默认。
- **Q5 自有 LLM**：line11 横切件——采纳推荐默认。
- **AI 通道对齐 active_org**：另有 multiorg agent 在定「多组织 + AI org 模型（active_org）」；路②的 AI 读/写文档身份与 org 归属要**对齐即将定的 active_org 模型**（WS 连接也要声明 org）。S4/S5 的「复用 req.workbenchIdentity」需与 active_org 对齐后确认最终形态。

## 判定结论（为什么它是一条独立的路）

三问法逐条过：① 客户会为「团队文档协作」单独点头/它出现在交付清单吗——**会**（「我们支持像 Notion 一样写协作文档了」，主理人原话方向要替代飞书/Notion 文档）；② 拿掉它旅程还走得通吗——**不通**（经验问答≠写文档，database≠富文本文档，两者都接不住「写一篇会议纪要/SOP」）；③ 有自己的起点和客户可感知终点吗——**有**（触发=要写文档，终点=文档写成、协作、被 AI 读用）。两把尺子：尺子①「支持写协作文档了」客户点头=路级；尺子②走完拿到的结果（一篇可协作、可被 AI 读写、按权限管的文档）与路①（一条被检索到的经验）、路③（一张结构化表）**结果本身不同**=独立路，非加厚。

⇒ **结论**：路②是 line11 下一条独立 Capability，与路①/③平级。地图现状：journey_feature 0c78270b 已登记名分但**尚无独立 golden_path**，本定义即为其立案草案（拍板后落 golden_paths，capability_code=`collaborative_docs`）。

## Gate 前置门（任一不过整条路停）

| 门 | 内容 | 断言 |
|---|---|---|
| G0 组织底座衔接 | 路②全部文档端点（含 WS 升级、AI 读/写端点）挂 workbenchAuthGuard：身份/org **只**来自服务端会话，禁读身份头、禁 body.org_id 生效、禁超管旁路、禁 selfHeal。A2 式静态守卫扫路②路由/service/WS 身份头字面量 | 持 B 企业真实会话+伪造 org_id 指向 A → 4xx/空集且 A 文档逐字未变；变异=改回读头即报红 |
| G1 富文本存储与 XSS 面（架构判定，呈拍板） | 正文存 **ProseMirror JSON doc → `documents.content jsonb` + version int**；用户输入的标题/正文永远只做数据值走绑定参数，SQL 注入面物理为零；渲染 XSS 由 ProseMirror schema 白名单收窄——**含节点/mark 属性协议白名单**（link href 仅 http/https/mailto，image src 禁 javascript:/data:），禁 raw HTML。**AI 写回入库过与人手同一条服务端 schema 校验**（防绕过写白名单外节点=存储型 XSS，risk P2-9） | 正文注入 `<img onerror>`/`href=javascript:` → 渲染后文本节点/协议被剥；标题含 `"; DROP` → 参数化不触发；AI 构造非白名单节点入库 → 服务端拒 |
| G2 备份底线 | 文档正文=企业核心资产，pg_dump 定时+异地+**恢复演练断言**（复用路③ G2） | 从备份还原到临时库，正文 JSONB 与关键字段逐条比对（L2）；演练进 cron 非一次性 |

## 承诺式骨干（5 步）

### S1 文档写得出、留得住——员工在文档树某节点新建文档，写富文本正文（标题/段落/列表/勾选/代码块/内嵌图片/@提及其他文档），保存后刷新还在，出现在本组织文档树；能移动/重命名/软删+30 天回收站；整篇可导出 Markdown 拿走

【挂片】文档树 UI（folder/doc 层级+拖拽移动）/ TipTap 编辑器（**跨 app 移植**+staff-hub 主题+schema 白名单含属性协议）/ 文档元数据表（`documents`：id UUID、org_id NOT NULL、parent_id、title、owner_member_id、visibility、deleted_at）+ 正文 `content jsonb`+version / 自动保存（防抖落库）/ 软删+回收站+删档二次确认（输入标题）/ Markdown 单档导出（数据主权底线，明写有损范围）/ db_audit 审计行

【分支/判定点】
- **⚠️ 正文存储形态（架构判定，呈拍板）**：推荐**整档 ProseMirror JSON 存 `documents.content jsonb`+version int**。理由同路③：唯一沿用现成隔离机械断言范式、注入面物理为零、无运行时 DDL。分块 `doc_blocks` 与 S2 协作粒度绑定（见 Q1）
- **⚠️ 内嵌图片存储（tech P2-3）**：图片二进制**禁 base64 入 JSONB**（撑爆行+放大整档写）；走对象存储，正文只存引用。Markdown 导出对图片/@提及/内嵌 database 的有损范围显式声明
- id 一律 UUID，反枚举；组织归属取 `req.workbenchIdentity.orgId`，绝不从请求体取
- 自动保存失败（弱网/500）必须编辑器可见并保留本地草稿，禁静默丢失（现状 CustomerListPage 全量重拉掩盖失败，不得继承）
- @提及其他文档：目标校验同 org + 请求者有权可见（无权/跨企业 id → 统一 404，不泄标题）

### S2 多人协作改得动、不打架——多个员工同时编辑同一篇文档时看得到别人在改，冲突时看到提示**而不是静默覆盖**，且**冲突方（loser）的改动本地零丢失、有可见的重存/合并入口**；断连时降级为只读+本地暂存并提示，重连走同一条冲突提示路径

【挂片】协作会话通道（WS，见判定点）/ 在线协作者指示 / 冲突检测与提示 UI / **loser 改动本地保留+重存入口**（把 S1「保留本地草稿」纪律延伸到冲突，product P0-1）/ 断连只读降级横幅 / 版本历史最小档（回看上一版）

【分支/判定点】
- **⚠️ 协作模型（本路最大架构判定，呈拍板 Q1）**：thin 走**整档乐观锁 + 冲突可见 + loser 零丢失**（提交带基线 version，不匹配 409+提示「该文档被 X 改过，你的改动已本地保留，点此重存」，禁静默 last-write-wins）。**诚实降级声明**：整档单 version 下两人改不同段落也会 409（tech P1-2），故 thin 承诺是「**不静默覆盖 + 冲突方零丢失**」，**不是**「多人同时改互不干扰」。真·实时字符级合并（Yjs/CRDT+doc_blocks 块级 version）作为**加厚**后刀。**乐观锁为本路净新增，非镜像路③**（路③实测无 version 列）
- **⚠️ WS 协作通道鉴权（risk P1-3）**：WS upgrade 不自动过 Express 中间件链→握手必须复用 better-auth 会话解析 memberId→orgId，协作房间按 **(org_id, doc_id) 强隔离**且每连接校验请求者对该 doc 有权（含 S3 编辑权限=协作准入，tech P2-1）。会话过期即断连重验（长连不静默续命）
- 断言：双会话同 version 各提交同文档 → 第二个 409、库值=第一个、**loser 正文可零丢失重新落库**；**变异**=注掉 version 检查/注掉 loser 保留断言必须转红。B 企业会话连 A 企业 doc 协作房 → 拒绝且拿不到任何在线/正文信号
- 并发洪峰：同文档 N 人改无死锁，乐观锁串行化落库

### S3 文档按权限管得住——文档/文件夹设可见范围与可编辑范围（组织可见 / 指定范围 / 仅自己 三档），权限沿文档树继承、**取父子更严者（most-restrictive-wins）**；无权的人看不到标题、不出现在树、搜不到、打不开、导不走、进不了协作、AI 检索不到

【挂片】权限设置 UI（每文档/文件夹选 visibility+回显**实际生效范围**）/ 继承解析器（most-restrictive）/ 树·搜索·打开·导出·@提及·协作准入·AI 检索**七处过滤** / 编辑权限校验（可见≠可编辑）

【分支/判定点】
- **⚠️ 三层中间层来源（呈拍板 Q3）**：现有员工目录只有 org+member 两层，**无部门/分组**。「指定范围」中间层落法：(a) 先两档中间层后刀 / (b) 显式指定成员集合（不建部门表）/ (c) 新建部门表（重）。推荐 (b)
- **⚠️ 成员集合生命周期（risk P1-4）**：成员集合命中后**必须 live 校验该 member 仍属本 org（查 tenant_members）**，禁只信静态 id 列表（离职+未失效会话=越权读）。断言：从 tenant_members 删除某 member 后，其对成员集合共享文档立即不可达
- **⚠️ 继承 fail-safe（risk P1-5）**：默认 most-restrictive-wins；把私密文档**移动进更宽父级不自动放宽**，需二次确认+回显。断言：设父级仅自己后，所有子档实际生效范围 ≤ 父级
- cross-tenant 由 Gate G0 兜底，本步管 **intra-org** 文档级 ACL；反枚举：无权与不存在统一 404、同文案、同响应形状；权限查询失败 → **fail-closed（503 不降级为可见）**

### S4 AI 读得到、答得准——员工让 AI 就本组织**自己有权看到的**文档答问/摘要，答案**带出处**；AI 只在请求者本人已鉴权的同步请求内、复用其身份检索，绝不召回请求者无权/他企业/未确认草稿的内容

【挂片】文档进检索域的索引（形态见判定点）/ ProseMirror JSON→纯文本抽取 / 带出处问答·摘要 / 自有 LLM 接线（line 级横切件 AI 助手层，复用路①）/ 权限前置过滤器

【分支/判定点】
- **⚠️ AI 读身份来源（risk P0-1）**：workbenchAuthGuard 是 cookie-only，后台 worker 无 cookie。**钉死**：AI 检索只在**请求者本人已鉴权的同步 HTTP 请求内、作为服务端工具调用、复用 `req.workbenchIdentity`**；**禁任何需自带身份的异步/后台 AI 检索**。断言：AI 读端点无 `req.workbenchIdentity` 即拒；变异=注入「无会话回落服务身份」报红
- **⚠️ 检索索引形态与前置过滤（tech P1-6/risk P1-6，呈拍板 Q2）**：index 行必须携带 org_id + effective-visibility；**权限过滤前置于召回**（禁先召回后过滤泄标题/片段）。索引类型 thin=关键词倒排、embedding 加厚（pre-filter 需向量库支持元数据过滤，列 Q2）。软删/权限收紧后**索引 N 秒内一致**（陈旧 ACL=越权召回窗口）
- **⚠️ 投毒防护分层（tech P1-4）**：**硬断言**=结构性防护存在（正文以数据分隔、来源标注、权限前置、输出不自动落库），可 psql/代码测 + **L3 真检索栈+真 LLM**（risk P1-7，禁 mock 召回）；**软断言（标「软」）**=「注入指令不改变答案」走 eval 集+LLM judge+人工抽样
- 断言：A 企业/无权成员/未确认草稿的文档**绝不进 B 的问答上下文**（构造跨企业+intra-org+pending 三类投毒文档验证不召回，L3）；变异=删投毒/权限过滤断言报红

### S5 AI 写得回、受同一权限约束——员工让 AI 把内容写回文档成**可见的「AI 草稿」块**，人工确认后才成正文；AI 写回**复用请求者身份+过 S3 权限校验**，只 additive 插入不整档覆盖，绝不以系统身份写他人私密文档

【挂片】AI 写回草稿块（pending 标记，不进检索直到确认）/ 人工确认闸（确认动作进 db_audit）/ additive 插入（禁整档 replace）/ 写回过 G1 服务端 schema 校验

【分支/判定点】
- **⚠️ AI 写回身份（risk P0-1）**：同 S4——只在请求者已鉴权同步请求内复用 `req.workbenchIdentity`+过 S3 编辑权限，**禁后台服务身份写库**。断言：AI 写回无请求者身份即拒；跨企业/越权写 → 4xx 且目标文档逐字未变；变异=注入服务身份回落报红
- **⚠️ 确认闸的真实边界（risk P0-2）**：确认闸只保证「未确认不成正文」，**不是投毒防护**（真防线是 G3③数据分隔+S4 未确认不进检索）；确认权归属需定义，**不能是投毒植入者自助确认**，确认进审计
- **⚠️ additive-only（risk P2-10）**：AI 写回一律插入草稿块，禁整档 replace（链式覆盖丢内容，1 版历史不足恢复）
- 断言：AI 写回落 `pending` 草稿块、S4 检索**不召回未确认块**；确认前删草稿块即撤销、确认后走版本回滚（后刀）；写回内容过 G1 schema 校验
