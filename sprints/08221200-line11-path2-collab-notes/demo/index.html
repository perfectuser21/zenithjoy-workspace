这条路是什么

员工在 Staff Hub 里写协作文档 —— 会议纪要 / SOP / 方案 / wiki —— 多人实时同编不打架、按组织权限管得住、AI 一等公民能读能写回且受同一权限约束不投毒。这条路要替代的是飞书文档 / Notion。

一句话触发器 → 终点：员工要写一篇文档（当前散在飞书/Notion/本地） → 建文档、写富文本、组织成文档树、多人 CRDT 实时协同、按组织权限管住、AI 能读能写回、数据按组织隔离可导出、删错可恢复。

4 道 Gate 全景 · 任一不过整条路停

本路碰四类真实世界接缝：生产 DB（文档正文=企业核心资产）、真实第三方 LLM、跨企业多租户真墙、WS 长连真机 E2E。故 S2/S4/S5 验证等级承诺必须 L3。

G0 / G0b

组织底座衔接 + WS 握手鉴权 本路最大接缝

全部文档端点挂 workbenchAuthGuard：身份/org 只来自服务端会话。但它是纯 Express cookie-session，不能 drop-in 到 WS 握手 —— G0b 净新增：WS upgrade 手写复用 better-auth 会话解析，多 org 成员命中 rows>1 拒绝不建房（绝不取 rows[0]），会话失效即断连重验。

G1

富文本存储与 XSS 面 · 本轮补 CV 校验点 P1-1

正文存 ProseMirror JSON → content jsonb，CRDT 存 crdt_state bytea；三条入库路径（HTTP 编辑器 / AI 写回 / CRDT-WS）过同一条服务端 schema 白名单（含 href/src 协议白名单）。CV = 服务端在 Yjs update apply 后落库前校验，拒绝裸 WS 客户端注入。

G2

备份底线 范式可照搬

文档正文 + CRDT state = 企业核心资产，pg_dump 定时 + 异地 + 恢复演练断言（复用路③ G2 范式，演练进 cron 非一次性）。

G3

文档纳入 AI 检索域 · 路② 独有命门 P1-2/P1-3

路② 文档进 QA 检索域（与路③ 排除相反）。三条不变式：① 权限过滤 = query-time live 复核（索引仅候选生成，召回后按 live ACL 复核，无权候选喂 LLM 前丢弃）；② 未确认 AI 草稿不进检索；③ 正文一律当不可信数据（分隔 + 来源标注）。

一句话风险提要

路② 最危险的不是「多人改冲突」，是三条越权通道：① CRDT/WS 走裸 socket 绕过 HTTP schema 白名单 → 存储型 XSS 还会被抽进 AI 检索（P1-1，已补 CV）；② WS 握手若对多 org 成员取 rows[0] → 把配置事故变成静默跨企业事故（P1-4，已钉硬断言+变异）；③ AI 检索只信索引态 ACL → 离职成员留下陈旧 ACL 越权召回窗口（P1-2，已改 query-time live 复核，零陈旧窗口）。这三条 R1 三镜头全部打到，v2 已逐条核销。

J1CRDT 库选型：实时同步引擎（净新增重决策）
推荐做法

REC = Yjs。官方 y-prosemirror + TipTap 官方协作扩展，字符级合并 + 多人光标（awareness）近乎开箱；本仓 TipTap 3.x 已是 dashboard 依赖。二进制增量 update 紧凑，天然适配 WS noServer 增量广播。

误判后果

选 Automerge：TipTap 无一等扩展，绑定/多人光标全部自研，工期翻倍且 merge 正确性风险。仅当首刀就要文档内建全量历史/时间旅行为一等需求才反选。

现场：CRDT 引擎零现成（git grep -i yjs\|automerge\|y-websocket 零命中）；路③ 无乐观锁/version 列可复用 —— 主理人 0822 拍板「实时版 CRDT（像腾讯文档）」，这是重决策、工程量大。

采纳 YjsAutomerge
J2WS 手写握手鉴权（cookie-only 不能 drop-in）
推荐做法

REC = 手写 upgrade 握手，auth.api.getSession({headers: fromNodeHeaders(upgradeReq.headers)}) → tenant_members 真查 → memberId+orgId；命中 rows.length>1（多 org）→ 拒绝不建房，绝不取 rows[0]（比照 workbench-auth.ts:92 的 409 语义）。抄 agent-ws.ts 的 noServer+upgrade+ping 模式但路径 /collab-ws 独立、鉴权换 cookie 会话。

误判后果（两种都不可逆）

① 直接复用 workbenchAuthGuard 中间件 → WS upgrade 不过中间件链 → 握手无鉴权 → 任意人进任意协作房；② 握手取 rows[0] 静默挑一个 org → 把配置事故变成静默跨企业事故。

现场：workbench-auth.ts 是纯 Express cookie-session 中间件，WS 握手够不着；agent-ws.ts 现有鉴权是 agent 机器 token（非 cookie 会话）—— 挂载模式可抄，cookie 会话握手 + 协作房 + 每连接 doc 权校验 + 多 org 拒绝 + 会话失效断连全是净新增。

采纳手写握手硬塞中间件（否决）
J4 / J5组织三层权限：显式成员集合 + live 校验
推荐做法

J4 REC = (b) 显式指定成员集合，不建部门表（员工目录只有 org+member 两层，无部门层）。J5 REC = 成员集合命中后必须 live 校验该 member 仍属本 org（查 tenant_members），禁只信静态 id 列表。

误判后果

建部门表 = 重且与飞书组织结构耦合；只信静态列表 → 离职成员 + 未失效会话 = 越权读。

关键：J5 的 live 复核范式就是 J6 AI 检索 query-time live ACL 复核的同一实现基座 —— 权限收紧后即时 fail-closed，读路径与 AI 检索路径共用一套。

采纳 (b) + live 校验静态列表（否决）
J6 / J10AI 检索投毒防护：live 复核 + CV 服务端校验
推荐做法

J6：默认纳入 =「有权可见即进」，ai_retrieval_opt_out 显式退出；index 仅候选生成，召回后一律 query-time live ACL 复核，无权候选喂 LLM 前丢弃 —— 正确性由 live 复核保证（真 fail-closed、零陈旧窗口），索引新鲜度降级为纯性能项。J10（本轮新增 CV）：服务端在 Yjs update apply 后落库前，对派生 doc 过与 HTTP/AI 写回同一条 schema 白名单，非白名单节点/协议拒绝该 update。

误判后果

只信索引态 ACL → 陈旧 ACL 越权召回窗口（离职成员内容仍被召回）；不做 CV → 裸 WS 客户端可绕过写白名单外节点 = 存储型 XSS + 污染 AI 检索；opt-in 才进 → AI 一篇读不到、「一等公民」当场打折。

四层投毒防护叠加：① 未确认草稿不进检索；② 权限前置过滤（live ACL）；③ 正文当不可信数据分隔；④ CV 覆盖 CRDT/WS 路径。人工确认闸不是投毒防护。
