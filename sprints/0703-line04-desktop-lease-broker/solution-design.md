# 方案：通用桌面资源仲裁层（Desktop Arbiter）

> 状态：**方案草案 v1，待用户审阅**。写在动手之前，先想清楚。
> 核心诉求（用户原话提炼）：不要又造一个"于姐让位给另一个客服"的点对点补丁；要一个**任何 agent 操作电脑都走同一套**的统一机制；不脑袋一热，先把顾虑和老坑理清楚形成坚实方案。

---

## 一、一句话问题

同一台机器上同时跑多个 line agent（微信客服常驻 + 抖音获客 + 发布器 + 将来任何要操作电脑的 agent），它们**抢整机前台焦点 / 键盘 / 鼠标**，互相打断，体感"一会儿被这个打扰、一会儿被那个打扰"，很尴尬，甚至互相把对方搞崩。

物理事实：**一台 Windows 交互会话，同一时刻只有一个前台窗口、一套键鼠输入**。所以"多个 agent 同时操作电脑前台"在 OS 层根本不可能真并行——**必须有人排队**。现在没有任何排队机制，各 line 进程由 module-manager fork 出来后各干各的，全靠运气不撞。

## 三、方案设计

### 3.1 立意：机制通用，策略特化（mechanism / policy 分离）

- **机制（Arbiter 本体，通用、agent-agnostic）**：一把机器级租约。谁想操作前台/键鼠 → `acquire(requester, priority)` → 拿到才动 → `renew` 续租 → `release` 归还。Arbiter 是"同一时刻谁能用桌面"的唯一真相源。它**不知道**微信/抖音是谁。
- **策略（配置进去，可调）**：谁是高优谁是低优、让位宽限多久、租约 TTL 多长。这些是参数，不是代码分支。

### 3.2 两层，概念一致但实现各自最简（回应顾虑 #5）

```
层2 = Desktop Arbiter（TS，在 module-manager）
      资源 = 整机前台焦点 + 键鼠
      管：哪个 line 进程此刻能用桌面
        │  （通过通用协议下发"你被授权 / 请让位"）
        ▼
层1 = 各 agent 进程内部自己的调度（各自最简，不强行统一）
      · 微信 listen_chat：现有 while 循环（不重构！见约束）
      · 抖音获客：它自己的 chrome 操作序列
      管：拿到桌面授权后，这个进程内部各动作谁先跑
```

**为什么不强求两层同一套代码**：层1 层2 天生不同语言（Python vs TS）、不同进程、不同资源，永远不可能是同一份实现。"统一"的正确含义是**概念同构 + 接口对齐**，不是同时重写两层。强并成一套抽象是为对称而对称，是过度设计的温床。

### 3.3 强制点：module-manager 收费站（回应顾虑 #4）

module-manager 是所有 line 的唯一 spawn 点，天然是收费站：
- 常驻 agent（微信）注册为"可抢占·低优"
- 一次性任务派发时，module-manager **先替它 acquire 高优租约**，拿到才放行 + 通知常驻让位
- 行业同款：UiPath/Robocorp 也是**调度层保证一台机器同一时刻只放行一个前台 job**，不是 OS 层锁键鼠

> ⚠️ **命门待验证**：module-manager 是不是真的唯一收费站？有没有子进程自己再 fork 孙进程绕过它去碰前台（比如 listen_chat 内部 spawn、获客 spawn chrome）？—— B 号调研正在查，出来才能拍死这条。

### 3.4 让位机制：优雅让位，绝不 kill

- 高优来 → Arbiter 给低优发"请让位"信号
- 低优**做完当前这一条原子操作**（比如微信正在发的这条回复）→ release → 退静默等待
- **信号复用现有文件控制通道**（listen_chat 已有 `_process_scan_control_file` 那套，再加一个"让位"控制文件，同构，不新造 socket/管道）
- **绝不 kill 微信**（kill 微信 4.x 必崩 —— 老坑，见约束）
- 宽限期（grace period）：低优收到让位后最多 N 秒内必须 release（做完手头这条）

### 3.5 防死锁：租约 TTL + 看门狗

- 持租方每 T 秒续租一次；超过 TTL 无续租 → Arbiter 判定它死了 → 自动回收租约 → 下一个顶上
- 防止：某个 agent 卡死/崩溃后一直占着桌面，别人永远饿死

### 3.6 通用协议（草案，所有桌面 agent 共用）

```
requester 描述： { id, kind: "resident"|"oneshot", priority: int }
动作：
  acquire(requester) -> granted | queued
  renew(requester)   -> ok | revoked      # 心跳续租
  release(requester)                        # 主动归还
  yield 信号（Arbiter→holder）：请让位     # holder 收到后做完原子操作即 release
状态机：idle → granted(holder) → yielding → idle
```

| **绝不 kill/重启微信来让位** | 微信 4.x 强杀必崩；#950 自愈重启曾把正在连续送达的微信打进多分钟死区 | wsb_reset_no_force_kill / reply_crm_scan_conflict |

## 五、什么进仲裁、什么不进 —— ⚠️ 待 C 调研确认

不是所有 agent 都要进仲裁。**只有真会抢前台键鼠的才进**：
- 微信 listen_chat（pywinauto/UIA 抢窗口焦点）→ **进**
- 抖音获客 / 发布器：如果是**前台浏览器自动化/键鼠模拟** → 进；如果是**纯 API 或纯后台 headless chrome（不抢前台）** → **不进**（进了反而白排队）

> C 号调研正在摸各 line 到底怎么操作电脑（CDP/pywinauto/API、前台还后台），出来才能定清单。

## 六、分阶段落地（机制统一 + 接入渐进）

| 阶段 | 做什么 | 范围 | 验证 |
|---|---|---|---|
| **第一刀** | Arbiter 本体（TS 纯逻辑）+ 通用协议 + 微信 listen_chat 最小让位接入（循环顶加守卫，不重构） | 机制通用、只接微信一个 | TS 单测(租约/抢占/看门狗) + module-manager smoke + Python 让位守卫 dry-run |
| **第二刀** | 真机验证"让位不 kill、微信自动续上" | windows_wechat 真机 | rog 清干净后真机跑 |
| **横向铺开** | 抖音/发布器等**各自实现同一协议接入**（彼此独立，可并行）| 多 agent | 各自 smoke；**此阶段用 agent teams 并行接入** |

**关键**：机制和协议**第一刀就做通用、做对**（不将就）；接入面**渐进**（不用一次接完所有 agent）。后续 agent 接入 = 再实现一次同一协议，**不改 Arbiter、不复制逻辑** → 这就是"统一机制"而非"补丁"的本质区别。

## 七、质量策略（怎么做不翻车）

- **核心第一刀（协议→Arbiter→微信接入）我自己串行做**：强依赖 + 高风险 + 需背全部老坑共识,subagent 局部视角最易掉链子。
- **subagent 用在**：前期正交调研（已在做）+ 一个独立 context 的**对抗审查 agent**挑我实现的毛病（新鲜眼睛是它的强项）。
- **agent teams 并行**留给横向铺开阶段（各 agent 接入天然独立）。
- **本方案文档写死 = subagent 的共享记忆**：文档定死后再切给 subagent/team 才安全。
