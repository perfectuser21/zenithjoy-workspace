# 结论:OpenClaw(小龙虾)不能解决"多 RPA 抢键鼠"问题

> 本文档已核实过真实源码(`gh api repos/openclaw/openclaw`)。之前几轮对话里提到的
> "PandaBoss-AI/clawrunner-workflows"、"43个skill"、"resource-lock源码" **全是编造的,不存在**,已作废,别再信。

## 最终结论

**OpenClaw = 个人 AI 助手网关**(把 AI 接到微信/WhatsApp/Telegram/Slack 等渠道,统一管对话/会话/多分身路由)。
它的"并发/队列"机制管的是**同一个 AI 会话里消息别互相打断**(聊天层面),不是"谁能操作电脑键鼠"。
它自己不做桌面鼠标键盘控制,要控制桌面得装第三方插件(Codex Computer Use / Peekaboo / cua-driver),
**这三个插件全部只支持 macOS,没有 Windows 桌面自动化能力**。

**我们的问题是:一台 Windows 机器上,微信 RPA(pywinauto/UIA)+ 抖音 RPA 同时抢鼠标键盘/前台窗口**——
这是操作系统层面的物理资源互斥问题,跟 OpenClaw 解决的"聊天消息路由/并发"完全是两个问题域。
**OpenClaw 用不上,不用再研究它,不要装。**

## 真实问题要怎么解决

自己做一个轻量的"机器锁"(此前叫 Desktop Arbiter / 桌面租约),别指望现成框架:
- 谁想操作前台/键鼠 → 先申请租约 → 拿到才动 → 用完释放并复位干净状态。
- 常驻(微信客服)低优先级,可被一次性高优先级任务(获客/发布)抢占。
- 让位 = 做完手头这一条原子操作后释放,**绝不 kill 微信**(kill 微信4.x必崩,老坑)。
- 看门狗:持锁方超时不续租,自动收回,防死锁。
- 强制点:挂在 `services/agent/src/module-manager.ts`(所有 line 进程唯一 spawn 点)。
  ⚠️ 但发现这个收费站本身有漏洞——子/孙进程会绕过它(`module-manager.ts:88-94,368-369`
  `child.kill()` 杀不到 fork 再 spawn 的孙进程,历史上因此出现过孤儿 listener 抢微信跑满 24h)。
  **真正落地前必须先补:进程树硬管控 + 单实例锁**,否则锁本身会被绕过。

详细的 11 条老坑约束(哪些绝不能做、为什么)在同目录 `solution-design.md` 第四节,仍然有效,
可以直接拿来当护栏用。

## 业务上还没确认的事实
一台机器上多个微信号能不能"后台并发"操作而不互相踩(不是能不能不抢前台,是能不能真并行)。
这决定锁的粒度:能并发 → 每个微信号一把锁(可并行);不能 → 整机一把锁(只能串行)。
需要真机验证,别猜。

## 下一步建议
1. 跟用户确认:不再研究 OpenClaw/clawrunner,回到"自己做机器锁"这个方向。
2. 先补进程树管控 + 单实例锁这个地基(否则锁形同虚设)。
3. 再做最小的锁本体 + 微信让位接入,真机验证。
4. 全程:先想清楚方案给用户审 → 再动手;不写点对点补丁,写通用机制(任何 agent 都走同一套申请/续租/释放协议)。
