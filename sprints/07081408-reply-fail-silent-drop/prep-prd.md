# Bug PrepPRD：发送失败后微信角标已清，冷却重试机制永远不会再触发，消息永久静默丢失

## 症状
2026-07-08 rog 生产实测：客户"默忆"发图片+"你叫什么"，机器人尝试回复但 `_uia_send` 送达确认读回失败（5次轮询共1.5秒，全部读到空预览），判定 `send_failed`，记录 60 秒冷却重试。但冷却时间到了之后，日志里再也没有出现任何关于这个人的 scan/回复记录，`unread` 直接从 1 变成 0——直接读当前聊天窗口气泡，确认客户的问题从头到尾没有得到任何回复。

## 根因假设
两层叠加：
1. **送达确认窗口偏短**：`_DELIVERY_READBACK_POLLS=5` × `_DELIVERY_READBACK_POLL_SLEEP=0.3s` = 总共只有 1.5 秒。代码注释显示这是从 3 秒主动收紧来的（"延迟收紧：成功通常 1-2 轮命中；失败窗口 3s→1.5s"）。图片消息较多的对话里，微信侧边栏预览刷新更容易跟不上这个窗口，读回假阴性概率上升。
2. **真正的致命根因**：`_open_chat`（打开会话尝试回复）这个动作本身会让微信把该会话标记为"已读"，清掉原生未读角标。发送失败后虽然代码记了 `reply_failed_at[key]` 冷却状态，但冷却重试逻辑只在 `unread`（=本轮 `scan_unread` 检测到的未读列表）里的消息上生效——一旦角标被清掉，这条消息永远不会再出现在 `unread` 里，`reply_failed_at` 的冷却重试条件因此永远没有机会被求值，消息被永久静默丢弃，且没有任何后续告警/补偿动作真正执行。

## 修法
1. `_DELIVERY_READBACK_POLLS` 从 5 提高到 10（对应总窗口从 1.5s 恢复到 3s，抵消收紧带来的假阴性概率上升）。
2. 新增独立于 `scan_unread`/`unread` 角标检测的待重试队列 `_PENDING_RETRY`：发送失败时记录 {sender, content, reply, failed_at, 尝试次数}；主循环每轮独立检查这个队列（不依赖角标重新出现），冷却到期后按 sender 名字重新扫会话列表拿新鲜 item 引用，主动重发；成功则清队列+提交 DELIVERED；连续失败达上限（如 3 次）才放弃并触发关键人告警（角色复用现有 `post_failure_alert`）。

## Regression Test 计划
- `test_reply_fail_retry_queue.py`（新文件）：
  - Case A：发送失败 → 消息进入 `_PENDING_RETRY`
  - Case B：冷却到期前不重试（幂等，不重复处理）
  - Case C：冷却到期后 `select_due_retries` 纯函数正确选出该 sender（不依赖 scan_unread 的 unread 列表——这是本次要证明的核心：即使角标已清，纯函数视角这条消息依然"待重试"）
  - Case D：重试成功 → 从队列移除
  - Case E：连续失败达上限 → 从队列移除且触发告警（不会无限重试卡死）
