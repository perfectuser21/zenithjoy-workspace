## 1. 背景：三个实测出来的问题

1. **evaluator 跑了但证据在腐烂**。Brain 库 `harness_attempts` 表有 76 次 evaluator 运行、44 次带结构化结果（每条检查含命令/预期/日志尾/退出码，判决分布 19 FAIL / 18 PASS / 2 带保留）。质量合格，但近半检查的证据路径指向 `/tmp` 日志——抽查两个均已不存在。判决在、凭据没了。
2. **report 几乎没产出过**。仓库里成文的 harness-report 只有 1 份（0720 sprint）；report 环节名义六步交付，0728 交接记录证实靠人工补录才走通过一次。主理人从未在任何页面看到过验收报告。
3. **人和机器验的不同轴，没法对表**。员工真机验收表（docs 文档中心，14 步 × 4 格）与 evaluator 的合同断言、32 步 canonical smoke 各验各的，维度对不上——出了分歧无从发现，"服务端全绿但真机体验挂了"这类历史最毒的假成功（全 mock 漏判 #1269/#1271、假 sent、WS 401 多症状）没有系统性捕捉手段。

另有一个未落地的主理人 idea：evaluator 应随机加扰动看稳定性。decisions 表查无登记；最接近的现存物是个别合同里的"×2 重复执行"（连跑两遍验一致性，8/2 实测靠它区分了稳定失败与抖动）。

## 2. 目标（用户语言：做完后主理人/员工能看到什么）

1. **一个对比页**：左列机器打的表、右列员工打的表，同构 52 格（14 步 × 4 要素格），四象限一眼可辨——双绿自动定案、双红实锤缺陷、"机器绿人红"高亮追查、机器空白格标"仅人工"。
2. **每个机器格子点得开证据**：命令、日志、产物链接，三个月后仍能打开（不再指向 /tmp）。
3. **每轮发版验收自动出一份报告**：落文档中心 + sprint 目录，不再靠人工补录。
4. **稳定性档**：对同一版本把全量断言跑 N 遍并加随机扰动，输出"哪些格子在抖"的清单。

## 3. 范围：四把刀

### 刀 1 · 验收规程 SSOT（地基，先行）
- 新建 `acceptance-spec/line02-android.yaml`：52 格逐格定义——稳定编号（如 `S07-C1`）、判据原文、**谁能验**（`machine_db` 机器可查 / `machine_visual` 机器可看 / `human_only` 必须人工）、对应断言引用（golden-path-2-smoke 的步骤号或合同断言 id）、症状选项码表。
- 员工验收网页改为从该文件生成（同 product-map.yaml → 生成投影的既有模式），消除"网页即规程"的双写。
- 版本字段显式化：规程按 APK 版本 + 后端提交号切面。

### 刀 2 · 机器表（evaluator 发版验收模式）
- evaluator 新增运行模式：输入 = 版本 + 规程文件，跑全量映射断言（预估首版可覆盖约 28~30 格），**逐格**输出结构化结果落库（复用 `harness_attempts.result.checks` 现有形态，补格子编号字段）。
- **证据死规则**：证据禁止只落 `/tmp`——必须进证据胶囊目录 / CI 产物 / sprint 目录三者之一，否则该格判决无效。写进 evaluator skill 红线段。

### 刀 3 · 对比页 + report 复活
- 文档中心新增对比页：读机器表（库）+ 人表（员工页导出的结构化结果，员工页补一个"导出本轮结果"按钮），按格叠合渲染四象限。
- report 节点在 judge 通过后必跑，产物落 sprint 目录 + 文档中心；连带修复 0728 已登记的"auto-merge 抢跑 judge"竞态。

### 刀 4 · 稳定性档（随机扰动）
- 先落 decisions：主理人拍板"evaluator 稳定性档 = N 遍重跑 + 随机扰动（断言执行顺序 / 时序抖动 / 良性输入变体）"。
- 实现：发版验收模式加 `--stability N` 参数；输出抖动格清单（同格多轮结果不一致 = 抖动）并入对比页。
- 现有"×2 重复执行"合同条款收编为本档的最小档位。

## 4. 最终验收（用户可见判据；合同阶段由 Contract AI 翻译成可执行断言）

1. 打开文档中心对比页，看到 2.1.19（或当时最新版）的一轮真实双表：机器列 ≥28 格有值、人列为员工真实打的一轮，四象限着色正确。
2. 任意抽一个机器"通过"格，点开能看到证据且证据文件/链接存活（负例：指向 /tmp 的证据必须已绝迹）。
3. 查库能看到该轮发版验收 run 的逐格记录（格编号 + 判决 + 证据地址）。
4. sprint 目录与文档中心各有一份本轮 report，非人工补录产物（以生成时间戳与流水记录为证）。
5. 稳定性档对同版本跑 3 遍，输出一致性报告；人为注入一个 flaky 断言（变异测试守卫原则）必须被标为抖动格——守卫本身要 proven-to-fire。

## 5. 非目标

- 不做 AI 驱动真机执行第 5~13 步（二期；本期机器表只覆盖服务端可查格）。
- 不做员工证据文件上传后端（证据包仍按现行文件夹规范外发；员工页只导出打分结果 JSON）。
- 不改 14 步业务定义与员工页交互形态（症状选择题等保持现状，仅数据源切到规程文件）。
- 不在本期对齐 Path2 业务 8 步与 smoke 32 步的编号（沿用 gp-anchor 设计既定口径：业务步 ≠ smoke 步）。
