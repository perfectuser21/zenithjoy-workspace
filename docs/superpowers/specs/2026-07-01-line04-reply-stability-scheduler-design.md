# Line04 微信客服回复稳定性重构 — 两层调度 + 回主界面 设计

> 状态：设计（待实施）｜作者：Lead ｜日期：2026-07-01
> 配套 memory：`line04_reply_stability_scheduler_redesign_plan_0701`
> 稳定基线：`git 74654efd`（6-21 B方案 #811，"回复特别稳"那版）

## 0. 一句话

回复"慢 / 不回 / 把字写进搜索框"的根，不是回复逻辑坏了，而是**多个功能（回复、扫好友、朋友圈）共用同一个微信窗口却不干净交接**。根治 = **每个 ability 独立队列 + 一次一个 + 每个 job 前后强制"回主界面"**。这套模式两层复用（line 内 / line 间）。**不删任何功能**。

## 1. 问题与证据

### 1.1 现象（用户 2026-07-01 真机报告）
- 回复**一会儿快一会儿慢、时间随缘**；发 2-3 句只回 1-2 句，**甚至不回**。
- agent 有时把回复内容**粘贴进微信搜索框**（不是聊天输入框），发不出去。
- "以前特别稳"（用户记忆），最近才开始烦。

### 1.2 退化时间线（git 实证）
| 时间 | 变化 | 影响 |
|---|---|---|
| 6-21 `74654efd` | B方案：简单回复（扫未读→开会话→发），1988 行 | **特别稳** |
| 6-25/26 `#891 #897-903` | 加 CRM 滚动扫好友（滚全列表 + 逐个开会话） | 立刻"回一次就不理" |
| 6-29 `#950 #955 #962 #965 #967 #968` | 一批补丁救它：树塌重启微信 / 窗口锁 / scan 回顶 | 复杂度堆进回复路径 |
| 现在 | 3453 行（翻倍）；自动扫好友虽已删(#967 只按钮触发)，补丁全留下 | 又慢又不稳 |

### 1.3 根因（双向核对）
- **回复函数本身几乎没变**（`scan_unread/reply_in_chat/_open_chat/_find_chat_input/_uia_send` 和稳定版一致）。
- 函数级已解耦（AST 查证）：回复路径**不调**扫好友/滚动/树塌重启函数。
- **冲突在共享资源：一个微信窗口**。扫好友滚到列表底、留草稿、挪窗口 → 下一轮回复**继承脏状态** → `_find_chat_input` 下半区找不到输入框 → 回退"全局最大 Edit"= 顶部搜索框 → 字写进搜索框、发不出。
- 树塌（微信启动时没带 SPI 标志 → 无障碍树塌缩）→ 现在靠"重启微信"救 → 每次重启几分钟死区 → 慢/随缘。

## 2. 现状调度（as-is）

### 层2（line 之间）：**无协调**
`module-manager.ts` 把每个 line（01/02/04/05）`fork` 成独立进程并发跑，**没有机器级锁 / 前台令牌 / 协调器**。现在不常撞，只因 line04 刻意不抢前台 + line01/2/5 任务触发大多闲。

### 层1（line04 内）：一个主循环
```
每轮：
 1. 拉指令：节流轮询中台「立即扫好友」force 标志
 2. 调度判定：_should_insert_scan = (force 且 无待回复未读)   ← 回复优先
 3. 若扫：run_friend_scan(120s 软超时) → finally 补 SPI
 4. 回复：scan_unread 读未读 → 逐个 reply_in_chat（发完还焦点）
 5. 外发：process_outbound_once（朋友圈/主动）
 6. 树塌检测 → _restart_wechat_for_uia（重启微信）
 7. 关更新 _relock_update
```
**四个缺口**：① job 间不回主界面（脏状态传染）② 扫一次独占 120s（期间消息干等）③ 树塌靠"重启"治标 ④ 层2 没有。

## 3. 目标架构：两层套娃调度

```
【层2·机器级】资源 = 整台机器的前台 / 鼠标键盘
   机器协调器（现在没有，Phase 3 再做）
      ├─ line01 队列（发布，任务触发）
      ├─ line02 队列（获客，任务触发）
      ├─ line04 队列（客服，常驻）
      └─ line05 队列（视频，任务触发）
      每个 line 拿令牌前后 → 回「机器中性态」

【层1·line04 内】资源 = 微信窗口
   微信窗口管家（做法二有雏形，Phase 1 补完整）
      ├─ 回复队列（高优先，可插队）
      ├─ 扫好友队列（低优先，空闲/夜间，切小块）
      └─ 朋友圈队列（定时）
      每个 ability 前后 → 回「微信主界面」

【叶子·ability】= 一个 job：归位 → 干活 → 归位
```

**三条铁律（两层同构）**：
1. 只有"管家/协调器"碰共享资源；所有活排队交给它。
2. 一次只放一个 job 出去，**干完把资源还原到干净基线**，下一个永远从干净开始。
3. 高优先（回复）可插队；低优先（扫好友）切小块或只在空闲跑，**绝不长占**；**任何 job 崩了/超时也强制归位**，不传染。

## 4. 「微信主界面(home)」定义

每次归位，把微信恢复成这个**唯一已知状态**：
- 窗口正常大小（不窄 / 不最小化 / 不离屏）
- 停在"微信"聊天 tab（不是通讯录/发现）
- 会话列表滚到顶部
- 无草稿（清空任何输入框残留）
- 不停在搜索框
- **SPI 屏幕阅读器标志在**（界面可读、树不塌）

> 每个 ability 都从这个同一界面出发 → 自动化步骤确定、可复现 = 稳。

## 5. 实施计划

### Phase 0 — 观测先行
- 中台 `draft-generate` / 回复关键日志**加时间戳**。
- 心跳**上报模块版本号 + 每条消息的跳过原因**（现在只报 `ok:true`，看不到版本，也看不出为什么没回）。
- 目的：客户机无 SSH 也能在中台看到"哪台、几版、这条几点回 / 为什么没回"。

### Phase 1 — line04 窗口管家 + 回主界面（治当前慢/不回）
1. 写"归位主界面"函数（§4 的动作全做）。
2. 每个 ability job 前后强制调用归位（崩/超时也归位）。
3. 主循环改成调度器：各 ability 独立队列、一次一个、回复最高优先、扫好友切小块/空闲跑不占窗口。
4. **每次拿窗口时重设 SPI → 树不塌 → 删掉 `_restart_wechat_for_uia` 那套**（顺序：先保 SPI，再删重启）。

### Phase 2 — 验证（真机）
- rog **先清干净**，验：① 回复稳 ② 扫好友跑完不干扰回复 ③ 某 job 崩了能自愈归位不传染。
- 客户机（同事那台）开机后复验。
- **纪律**：看到"默忆真收到 + 不写搜索框 + 扫好友不打断回复"才算 done，不信中台日志的 `auto-send`/`DELIVERED`（都栽过）。

### Phase 3 — 层2 机器协调器（line 变多/GUI 冲突变多时）
- 同一套调度抽象往上套一层，资源换"整机前台/输入"；机器令牌 + 回机器中性态；常驻 line04 在偶发任务来时让位。

## 6. 可独立先做的 ⚡ 小修（不用等全重构）
1. **输入框绝不回退到搜索框**：`_find_chat_input` 下半区找不到聊天输入框时，**中止本轮，绝不回退"全局最大 Edit"**（那是顶部搜索框）。
2. **真送达判定鲁棒**：读回 preview 空/慢别一次就判失败重发（防重复 + 延迟）；理想读聊天面板真气泡而非会话列表预览。

## 7. 不做什么
- **不删扫好友**（将来要用）；用隔离，不用删。
- **不再往回复路径加"滚动/开群"**（#998 的错误，已 revert，守卫 `test_reply_loop_purity` 锁死）。
- **不再加"塌了就重启"补丁**；从源头保 SPI。
