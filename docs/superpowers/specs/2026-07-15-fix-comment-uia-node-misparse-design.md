# 设计：修复抓评论 UIA 节点误判(把点赞数/日期/评论数标签当成 lead)

## 背景与问题

获客链 Seg3(抓评论)在 staging 上跑通了流程,但抓下来的数据是垃圾：把评论区的"7889条评论"标题栏文本、排序 tab("热门"/"最新")、日期(如"07-15")、点赞数(如"1.2万")当成了评论人昵称/正文采进 `commenter_id`/`text` 字段。

## 根因

`services/agent-android/app/src/main/kotlin/com/zenithjoy/agent/collect/NodeExtractor.kt` 的 `extractComments`：
1. 方案一(`extractByResourceId`)因 resourceId 候选值未经真机验证,几乎总是命中不了,兜底掉到方案二。
2. 方案二(`extractByStructure`)靠"相邻文本对 + 长度 1~20 字符 + 5 词黑名单"判断是否"昵称+正文"，判据过宽：标题栏、排序 tab、日期、点赞数字符串都落在同样的形状里，被误判为真实评论。
3. 更深层：`DouyinCollectService.kt` 的 `flattenNodes` 用 BFS 展开无障碍树，打乱了同一条评论内"昵称→正文→元信息"子节点的相邻视觉顺序，让"相邻配对"这个假设本身就不成立。

参考修复模式 PR #1294(取分享按钮同类问题的解法)：不信任遍历拿到的第一个候选，收集全部候选，交给一个独立、可单测的纯函数按结构/几何特征做二次筛选，筛不出就放弃这次采集（宁可漏采不误采）。

## 方案

只有一个可行方案（问题定位已经很明确，不存在多个架构级备选）：

1. **`NodeExtractor.kt`**：新增独立纯函数 `looksLikeMetaLabel(text: String): Boolean`，收纳所有"这不是真实昵称/正文"的判据：
   - 纯数字/数字+单位（点赞数）：`^\d+(\.\d+)?[万kK]?\+?$`
   - `^\d+条评论$` / `^共\d+条评论$`
   - 日期格式：`^\d{1,4}-\d{1,2}(-\d{1,2})?$`
   - 排序 tab 词表：`{"热门","最新","查看更多回复","展开更多回复","IP属地"}` 及 `^IP属地[:：]` 前缀
   - 在 `looksLikeNickname`/`looksLikeContent` 判断中调用该函数做拦截
2. **`DouyinCollectService.kt` 的 `flattenNodes`**：BFS 改 DFS 前序遍历，保证同一评论 item 内部子节点在展开列表里保持视觉上下相邻。

**范围收窄（YAGNI）**：原计划中"给 `NodeInfo` 补 `boundsInScreen` 做几何锚点二次筛选"的第三点本次不做——三条已确认的 regression case（标题栏/点赞数/日期误判）靠黑名单正则 + DFS 顺序修正已经能全部拦住，没有测试逼着要一个没法验证的几何匹配层。真机验证如果发现黑名单覆盖不到的新误判模式（比如同层级但视觉不相邻的干扰文本），再补 bounds 锚点，到时候有真实失败样本能写成测试，比现在凭空加一层没有失败用例驱动的结构判断更扎实。

## 测试计划

`NodeExtractorTest.kt` 新增 regression 用例（纯逻辑，白盒，不需要真机）：
- `"7889条评论"` + `"最新"` 相邻 → 不产出 entry
- 昵称 + 正文 + 点赞数`"1.2万"` 三元组 → 只产出 1 条，点赞数不进 text，也不被误当下一条 commenterId
- 日期`"07-15"` 紧跟真实昵称 → 不误配对

这是逻辑接缝（纯函数解析），CI test 即为 proven-to-fire 守卫，不需要额外的真机/运行时自检。

## 风险与边界

- 黑名单词表/正则是启发式，无法保证 100% 覆盖所有元数据变体；后续如真机验证发现新的误判样本，追加到黑名单即可，不需要动架构。
- resourceId 精确匹配路径（方案一）本次不做真机验证，维持现状（如果哪天真机验证通过，会天然优先于方案二生效，不冲突）。
