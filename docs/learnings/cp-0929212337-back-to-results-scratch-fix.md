## back_to_results误判暂存草稿页为真结果页(2026-09-29)

### 根本原因

`current-video-link`取链接时会打开一个"暂存草稿页"(`search/tabs?keyword=%20`)专门
用来粘贴剪贴板内容解析短链。这个草稿页跟真搜索结果页是**同一个 Activity**
(`SearchResultActivity`)，`_is_search_results_fg`只判 Activity 类型，天生分不出来。

真机逐字节比对实锤：`back_to_results`报告`back_to_results=1 backs=1`(自认成功)，
但重新扫描拿到的 UI 树跟`current-video-link`内部草稿页解析步骤的 UI 树**逐字节完全
相同**——人根本没离开过草稿页。12个关键词的真实生产日志显示：每个词4张候选卡片，
只有第1张能处理，第2/3/4张**100%**报"视频链接解析失败(VID=空 VURL=空)"。

这不是新引入的bug——`_current_video_link_once`/`back_to_results`都是老代码，
0922夜批就修过一次同类问题("退到看见结果页为止"，不数back次数)，但那次修法的
判据本身不够精确，只堵住了"退到完全不相干的页面"，堵不住"退到同Activity但其实是
草稿页"这种情况。而是9/29 DoD审计批次3/4新加的"VID/VURL为空就跳过不处理"这层
安全检查，把这个一直存在的老问题**曝光**了——过去它会静默产出全空的脏数据，
现在会诚实报错跳过。

### 修复分三层

1. **精确判据**：新增`_search_kw_matches`纯判定——真结果页搜索框是干净的原始关键词
   (如"人工智能")，草稿页搜索框是一整段分享文案+短链+追踪码，两者天差地别，不需要
   碰任何 resource-id(混淆过的，跨版本不稳定)。`back_to_results`传入关键词时，
   Activity判真之后再核一遍这把尺子。
2. **确定性兜底**：真机测试发现单靠"多按几次返回键"赌不赢——长时间在线设备的
   back栈深度不可预期(实测按满4次后落在了跟本次搜索完全不相干的历史搜索页)。
   重试耗尽后不再赌栈深度，直接重新发起本次搜索的意图，不依赖任何历史导航状态。
3. **调用方联动**：兜底重搜会重置筛选条件，页面上卡片顺序/内容随之变化，调用方
   (`harvest-keyword.sh`)一开始扫描存下的坐标全部作废。把主循环从固定 for-each
   改成可变数组+索引的 while 循环，命中兜底重搜就立刻重新扫描卡片并重置索引，
   外层循环从新列表头继续处理剩余候选。

### 下次预防

- [ ] 判断"是否已归位/是否在正确页面"这类判定，只看 Activity/包名这一层粒度
      往往不够——同一个 Activity 可能承载完全不同的业务语义(真结果页 vs 内部
      临时解析页)，需要下钻到页面内容(本例是搜索框文字)才能真正区分。
- [ ] 涉及真机 back 栈导航的恢复逻辑，"多按几次返回键"不是可靠的通用解法——
      长时间在线设备的历史栈深度不可预期。凡是"应该退到某个已知目标页"的场景，
      优先考虑"直接重新发起能确定性到达目标页的意图/深链接"，把它当唯一可靠兜底，
      而不是无限加大重试次数。
- [ ] 任何会导致"页面内容重新洗牌"的恢复/兜底动作(比如重新发起搜索会重置筛选)，
      调用方如果缓存了这个页面的坐标/内容列表，必须在恢复动作触发后让调用方知晓
      并重新获取，不能假设恢复=坐标依然有效。
- [ ] 本次修复暴露了一个真机testing环境的真实教训：同一段真机自动化代码，
      连续跑4次里有2次卡在一个完全无关的"筛选面板选项点不中"问题上——这类
      纯真机UI操作偶发失败率不低，验证一个bug修复是否生效时，遇到"跑不完整
      流程"不要立刻怀疑自己刚改的代码，先看失败点是不是在自己改动范围之外，
      针对性地用更底层的直接命令调用绕过去验证核心逻辑，比死等一次完整流程
      跑通更省时间。
