## phone-adb-controller merge到main自动部署三机（2026-09-29）

### 根本原因

这条产线（智能获客/关键词获客，控制真实安卓手机自动给真实客户发抖音私信）的部署机制
`services/phone-adb-controller/deploy.sh` 从建立起就只能人肉手动执行——GitHub 合并只更新了
"配方书"，真正跑在生产上的是 mmv 本机 + 西安 xian-m4/xian-m1 三台物理机上的手工拷贝。
0929 实测：DoD 审计批次4（PR #2006）merge 到 main 后 6 小时，三台机器仍在跑批次3的旧代码，
直到主理人要求立即真机验证才发现并手动补跑 `deploy.sh`。

给这条线补自动部署的过程中，subagent-driven-development 的三轮任务审查+两轮全分支终审
一共揪出 2 个 Critical + 6 个 Important（含最后一轮修复本身引入的 1 个回归）：

1. **heredoc 假绿（Critical）**：SSH 远程执行块里调用 `deploy.sh`/`drift-check.sh` 时没有
   重定向 stdin，会把 heredoc 剩余的脚本内容当成自己的 stdin 吃掉，导致后续步骤全部被跳过、
   job 却仍然是绿的。已在 mmv 上实测复现。
2. **自举死锁（Critical）**：原设计在 `git reset --hard` **之前**从当前（未同步的）工作区
   source 判定 lib，第一次跑该文件还不存在，`set -e` 下直接退出；即便跑过一次，之后每次用的
   也是上一版本的 lib，形成死锁。
3. **安全闸误伤（Critical 的连带问题）**：mmv 主 checkout 长期存在 `.cecelia/`、`sprints/...`
   等 `/dev` engine 工作过程产生的未跟踪目录残留（不是这次部署造成的）。"工作区干净判定"函数
   如果把未跟踪文件也算作"不干净"，这道安全闸会永远触发，自动部署一次都跑不成功。
4. **重跑旧 run 会静默回滚生产（Important）**：GitHub Actions 的 "Re-run jobs" 用的还是那次
   触发时的旧 `github.sha`；如果期间又合并了新 PR，重跑会把三台机器的版本往回拨，而且
   drift-check 用同一个旧 SHA 对账，会显示"部署成功"。
5. **部分部署时告警文案空洞（Important）**：`deploy.sh` 被 `set -e` 杀死时来不及打印任何失败
   标记行，"提取失败原因"的 grep 结果是空的，Bark 正文只剩"deploy.sh语法检查失败: "，
   没有任何细节，还容易把排障方向带偏（这种场景下三机版本很可能已经不一致，且仍在正常发私信）。
6. **孤儿测试（Important）**：新写的两份 `.test.mjs` 没有接进任何 CI job，包括钉住"heredoc假绿"
   修复的那条测试——写了测试但没让它在 CI 里真的跑，等于没有回归保护（仓库里 PR#1769 就是
   同一类事故的先例）。
7. **修复本身引入的回归（R1）**：给 grep 结果做"为空则退回 tail"处理时，命令替换赋值语句
   `VAR="$(... | grep X | ...)"` 在 `set -euo pipefail` 下，grep 找不到匹配时的非零退出码
   会直接杀死整个远端脚本——比修之前更差（修之前至少 notify 参数里的 grep 空结果只是让正文
   为空，脚本还能继续跑下去发出这条告警；修完之后变成"告警本身都发不出去"）。

### 下次预防

- [ ] 给无人工确认闸、直接操作生产物理设备/真实客户触达的自动化流水线做设计时，"部署前安全检查"
      的判定条件必须先在目标机器上实地核对真实现状（`git status --short` 实际输出是什么），
      不能只凭理论设计——理论上合理的判定条件，遇到目标机器长期存在的正常残留文件，可能导致
      安全闸100%误触发，这条流水线为此专门核实过 mmv 的真实 `git status`。
- [ ] SSH heredoc + 内部命令读 stdin 是经典陷阱：heredoc 内任何会读 stdin 的命令（不只是显式
      读输入的程序，任何默认继承 stdin 的子进程）都必须显式 `</dev/null`，否则会吃掉 heredoc
      剩余内容导致脚本"提前结束但退出码为0"的假绿，这类问题在本地测试环境很难复现，必须在
      真实 SSH 会话里验证。
- [ ] `set -euo pipefail` 下任何"允许失败、失败也要继续执行后续兜底逻辑"的命令，必须显式
      `|| true`（或用 `if`/`&&`/`||` 包裹），不能假设"这行只是取个值，失败了也无所谓"——
      赋值语句本身的非零退出码一样会触发 `set -e`。
- [ ] 每次自动部署工具产出的判定基准（比如"部署成功"的对账 SHA）都要跟"这次实际部署的目标"
      绑定，不能依赖执行环境里可能已经继续前进的默认值（比如 `origin/main`），否则重跑/并发场景
      下会产生"用旧基准对旧结果，判定通过"的假阳性。
- [ ] 新增的测试文件写完之后，必须显式确认它已经被接进某个真实会跑的 CI job（用 `grep`/`gh`
      核实触发路径和 glob），不能假设"写在 `__tests__/` 目录下就自动会被跑到"——本仓库同类型
      教训（PR#1769）已经复发过至少一次。
- [ ] 对"生产直推无人工闸"这类流水线，subagent-driven-development 的多轮审查（逐任务 review
      + 全分支终审 + 复审）是值得的：本次两个 Critical + 六个 Important 里，有一半是在"看起来
      已经改完准备合并"之后的复审阶段才被发现的，包括最后一轮修复自己引入的新回归。
