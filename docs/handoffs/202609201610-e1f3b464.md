# Handoff：建任务写超时 3s→8s + 无响应重试一次（真机连丢两单触达的根因）

- task_id: e1f3b464-7a1e-4ed0-bd27-c419a0411b4b · journey: 24987ee5-53a0-4c37-946f-1b749954cac7 · verdict: PASS · PR: [#1892](https://github.com/perfectuser21/zenithjoy-workspace/pull/1892)

## 完成
- **根因实证**（不是假设）：`wall-report` 的 `api()` 用 `curl -m 3`。跨境抖动时服务端已 201 建好任务、响应回不来，客户端拿 000 按「静默降级」删状态文件 → 后续 `step`/`done` 全部「无进行中任务,忽略」→ 服务端留下孤儿 running 任务，10 分钟租约过期判 `executor_lost`；期间该设备新任务 `start` 一律 409（清扫只扫本机状态文件、扫不到孤儿），于是连丢第二单。
  - 现场：M4 `phone-wall.log` `[0920-13:33:45] start ANGYVB4402004137 HTTP 000,静默降级`，同刻 staging 库里 `3cf2b276` 是 running、两步 pending、`current_step=0/2`，而 `outreach.log` 显示这单 1 分半就「✅ 送达」。
- **修**：新增 `API_TIMEOUT_WRITE`（默认 8s，与 `register` 同档）用于 `start`/`complete`；`step`/`note` 是高频心跳仍 3s。`start` 收到 000 重试一次（第一次真失败则这次成功；第一次其实成功则这次拿 409，落进已有清扫分支）。
- **测试**：两条 regression test 先红后绿（假中台新增 `taskDelaysMs` per-call 延迟 fixture）；变异自证——超时改回 3s → 第一条红，去掉 000 重试 → 第二条红；全量 50 单测两种 bash 绿。已部署 M4/M1。
