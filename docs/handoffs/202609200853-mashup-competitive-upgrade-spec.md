## 方向一：文案解析出动态分段结构（难度：低）

**要做什么**：用户粘贴一段文案 → 调用现有 TOAPIS/Gemini 接口（已有凭据、已有调用模式）解析出 N 段结构，每段给出角色标签（如"开场钩子/痛点引入/产品介绍/案例证明/行动号召"）+ 建议素材数量。

**可直接复用的现成能力**：
- `apps/api/db/migrations/20260919_010000_mashup_slot_templates.sql`：`mashup_templates.slots` 字段本来就是 **JSONB 数组**，天然支持任意 N 个槽位，不是只能存 4 个——**不需要 schema 迁移**，现在的"固定四槽位"只是因为 seed 数据写死了一条模板，代码层面从来没限制过槽位数量
- `apps/api/src/services/mashup-render.ts` 里调 Gemini 的 `buildSafetyPrompt`/`axios.post(TOAPIS_BASE + '/chat/completions', ...)` 这套调用模式可以直接照抄，换一个新 prompt（"解析这段文案的分段结构"）即可

**要新增的**：
- 一个新服务 `mashup-script-parsing.ts`（起名随意）：输入文案文本，输出 `{ segments: [{ role: string, suggestedCount: number, matchTags: string[] }] }`
- 一个新路由 `POST /api/mashup/templates/from-script`：调用上面的服务，把解析结果落成一条新的 `mashup_templates` 行（`tenant_id` 归属到发起用户的租户，不再是内置的 `tenant_id IS NULL` 全局模板）
- 前端：在 PickStep 之前加一步"粘贴文案"输入框 + 解析结果确认/微调 UI

**判定点**：解析出的 `matchTags` 要如何跟素材已有的 `ai_tags` 对齐？现有 S1 打标签用的标签体系（"开场/悬念/产品展示/使用场景/行动号召"这类）是否够用，还是文案解析出来的分段角色需要一套新的标签体系、S1 打标签也要跟着扩展？——**这个要下赛程 PrepPRD 阶段跟用户确认**，不是纯技术判断。

## 方向三：候选生成到 200+ 条并可视化浏览（难度：中，但思路要换）

**要做什么**：候选列表从现在的十几条纯文字，变成 200+ 条、每条带缩略图、可滚动浏览。

**关键判定点（必须先定下来，否则会把服务器 CPU 打爆）**：
**200+ 条候选绝对不能每条都真实调 ffmpeg 渲染一遍视频**——参照这次会话跟用户对齐过的信息：hk-vps 只有 4 核 CPU，同时跑生产API/数据库/n8n等一堆服务，200 次真实 ffmpeg 编码会直接把机器打死。

正确思路：候选的"预览"应该是**素材缩略图的静态拼贴**（每个槽位取该素材的一帧缩略图，横向拼成一张"分镜卡片"图），**只有用户最终选定某一条候选时，才会像现在这样触发一次真实 ffmpeg 渲染**——这跟现有架构完全兼容，`mashup_candidates` 表本来就只存槽位组合的元数据，不存真实视频，改动集中在"生成候选时顺带算一张拼贴缩略图"这一步。

**可直接复用的现成能力**：
- `apps/api/src/services/video-frame-extract.ts` 的 `extractFrameBase64`（已用于 S1 AI 打标签的抽帧）可以原样复用来给每个素材抽一帧当缩略图素材
- `apps/api/src/services/mashup-candidate-generation.ts` 的 `HARD_MAX_TARGET_COUNT = 300`、`generateCandidates({ targetCount })` **已经原生支持 300 条以内的任意目标数**，前端把 `targetCount` 从默认值调到 200+ 即可，后端候选生成逻辑本身不用改

**要新增的**：
- 素材首次上传/打标签时顺带存一份缩略图（抽帧结果存 COS，`materials` 表加一列 `thumbnail_key` 或直接复用 `ai_description` 旁边加字段）
- 候选生成时，把槽位填的素材缩略图路径带出来，前端拼成分镜卡片
- 前端候选列表要做**虚拟滚动**（200+ 条 DOM 节点直接渲染会卡），不是简单加个 `.map()`

## 方向四：候选内直接剪辑（难度：高，两条技术路线二选一——下赛程 PrepPRD 阶段拍板）

这是四个方向里工作量最大的一块，量级跟这次会话做的 S1-S4 加起来相当或更大。有两条完全不同的技术路线：

### 路线 A：自建网页版轻量剪辑器
- 需要一个前端时间轴组件（拖拽调整片段顺序、换素材、微调时长）
- 保存时把编辑结果转成新的渲染参数，调后端重新 ffmpeg 渲染
- **优点**：全程留在自己的网页产品里，不依赖用户本机装什么软件，不依赖第三方格式
- **缺点**：从零造一个视频编辑器 UI，工作量大，且要处理时间轴交互的一堆边界情况（拖拽冲突、撤销重做等）

### 路线 B：导出剪映（CapCut）工程文件，让用户在剪映里编辑
- 剪映的工程文件格式（`draft_content.json` 等）没有官方文档，但已被社区逆向破解，有开源库（如 `pyJianYingDraft` 一类项目）能程序化生成剪映草稿——国内不少批量视频工具确实是走这条路，思路是可行的、不是空想
- **优点**：不用自己造编辑器，用户用的是自己熟悉的剪映客户端，剪辑体验直接是剪映原生水准
- **缺点（必须如实说清楚，不是"很简单"）**：
  1. 剪映工程文件里素材引用的是**本机绝对路径**，不是云端URL——意味着我们生成草稿的同时，还得把候选用到的素材文件打包（zip）给用户下载到本机指定位置，剪映才能正常打开这个草稿，不是"生成一个文件链接点开就行"
  2. 格式是逆向出来的、非官方的，剪映客户端升级有可能改内部格式导致我们生成的草稿打不开，需要长期维护跟进
  3 只能给到装了剪映桌面/APP客户端的用户用，纯网页端用户不能用这条路

**建议**：下赛程 PrepPRD 阶段，把路线 A/B 的取舍作为一个明确的"拍板点"抛给用户决定，不要在技术方案阶段自己悄悄选一条——这直接决定了这一块的工作量和产品形态。
