## 主理人拍板的两条硬要求

1. **所有的活必须留痕，他只在页面/Notion 上看。**
2. **不要 Mac 上的 crontab 定时。**「什么时候干什么」不能只存在于两台 Mac 的命令行里。

## 一条不能破的红线

**手机/Mac 不能直连 Notion 读写任务。** 三条理由，缺一条都能让方案崩：

| 约束 | 实测数据 |
|---|---|
| Notion API 限流 3 请求/秒 | 四台手机一天约 240 单触达 × 每单 4 步 ≈ 千次写，必被限流 |
| 投影有延迟 | Brain 写入到 Notion 出现：实测 118s / 482s / 963s / 2693s / 3090s。看排期够用，当执行队列会丢活 |
| CLAUDE.md 铁律 | 「AI 写库一律走 Brain API，禁止直写 Notion 投影表——直写＝账实分叉」；决策 e1ec93b2「Brain tasks 表＝唯一真身，Notion Task DB＝投影」 |

**所以「走 Notion 留痕」的正确实现是：写 Brain（真身）→ 自动投影 Notion（主理人的窗口）→ 人在 Notion 改 → 回流 Brain。**

## 要做的四件事

### ① Brain 侧：让手机的活成为任务单

- 新 `task_type`：`device_job`（或复用现有命名，自行决定但要与 harness 任务区分开）
- 必填：`dept`（智能获客 / 新媒体部 / 私域客服 / 视频剪辑）、`assigned_to`= `agents.id`（UUID，与控制塔同一把钥匙）、`due_at`= 计划时刻、`recurring_task_id`（周期展开的填规则 id，一次性单据留空）
- `metadata` 带：`serial`、`profile`（jinoshengyuan-work / legacy / …）、`est_minutes`、业务参数（词数、平台、内容 id）
- **周期规则**存一张小表或 `tasks` 里的规则行，Brain tick 每天提前 48 小时展开成具体任务单 —— 这样主理人今天就能在 Notion 看到后天的安排

### ② Mac 侧：crontab 只剩一条

- 删掉六条采收 cron 与触达 tick 里写死的序列号/词数
- 换成一条 `*/1 * * * *` 的领单器：`GET /api/brain/tasks?assigned_to=<本机所辖 agent>&status=queued&due_at<=now` → 认领（复用已有 claim 语义，防重复领）→ 调既有 `harvest-cron.sh` / `outreach-tick.sh` 的**执行部分**（它们的调度部分废掉）→ 回写状态
- 执行明细继续走 `wall-report.sh` 打到 hk-vps 的 `worker_tasks`（**不要灌 Notion**），控制塔实时页不受影响

### ③ 额度上移

- `dm-count-*.txt` 与 `dm-daily-cap.js` 的结果每次变更上报 Brain（或 Brain 主动拉），落在任务单或单独的配额表
- 页面上的额度条才会变成真实数字

## 已知坑（别重踩）

- **部门取值要归一**：「新媒体」与「新媒体部」并存
- **Notion 投影延迟最长实测 51 分钟**：所以 Notion 只能是窗口，队列必须在 Brain
- **一天 240 单触达不要每单都投 Notion**：Notion 保持「一台机器一天几条」的粒度（今天的采收轮次、今天的触达额度），逐单明细留 `worker_tasks`
- **领单要防重复**：同一 agent 同时只能有一条 running（`worker_tasks` 已有此约束，Brain 侧也要有）
- **写请求超时**：`wall-report` 刚踩过坑，跨境写请求 3 秒不够，关键写操作给 8 秒并重试一次（PR #1892）
